## 1. 结论摘要

真正吃时间的**不是写代码**——本阶段代码量很小（3 个新文件 `linkcheck.ts` / `install.ts` / `link.ts` + 3 处接线），成本集中在三件事：

1. **22 次子代理派发的冷启动重读**（有效 19 次 + 我自己浪费的 3 次空派发）。每个 subagent 是隔离上下文，必须重新 Grep/Read 建立理解。
2. **测试全量复跑冗余**：`pnpm verify`（tsc+build+unit+e2e 四段）≈ **12 次**，`vitest run tests/unit` ≈ **20 次**（推导值），主要由「实现者跑一遍 + 评审者再独立跑一遍」造成。
3. **OCR 单次全文件模式**：**4m58s / 3,388,389 tokens**（实测）。

在此之上，我自身制造了三类**零收益循环浪费**（无效派发 / 重复 skill 加载 / TodoWrite 连发），这部分**在账本里一个字都没有记录**——账本只覆盖技术裁决，不覆盖流程低效。

## 3. 耗时但**不该砍**的部分（防过度优化）

| 项 | 耗费 | 买到什么 |
|---|---|---|
| SDD 逐任务「实现者 + 评审者独立复跑」 | 15 次派发 + 多轮全量测试 | 抓到真实缺陷：**T2-10**（控制者勘误未同步到产出 fixture）、**T3 I-1**（execa ^10 `reject:false` 失败以 Error 实例 resolve，导致警告原因串降级） |
| OCR 评审轮 | 4m58s / 3.39M tokens | 抓到 **O1 critical**：`PackageManagerId` 逻辑 id 被当可执行文件名传给 execa → yarn 项目 install 与 `--watch` **恒定 ENOENT**。**SDD 五轮 + 终审全漏**（藏在执行语义而非契约文本里） |
| spec multi-lens 评审 ×4 轮 | 4 轮收敛 | 2 P0 + 5 P1 + 5 P2 全闭环；其中 **F1** 是真实数据损坏路径（批量链接同文件改写互相覆盖） |

**结论**：问题不在「验证太多」，而在「验证粒度未分级」。前述 P0 #1/#2 的解法是**分级**，不是**削减**。
